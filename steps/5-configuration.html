把配置理清楚

Configuration

看懂 ~/.hermes/ 目录，再动手改配置

你已经能和 Hermes 正常对话、也会切换模型了，但一遇到「换台电脑」「老师给了一个新 API Key」「想改掉 agent 的说话风格」这类事，就不知道该从哪个文件下手。这一节把 ~/.hermes/ 目录拆开看清楚：每个文件负责什么、同一个设置被好几处写的时候谁说了算、以及改完怎么让它真正生效。

◆学习目标

  • 说清 ~/.hermes/ 下 config.yaml、.env、auth.json、SOUL.md、memories/、skills/、cron/、sessions/、logs/ 各自负责什么

01这一步在解决什么#

Hermes 装好就能跑，是因为它替你把所有默认值都填好了 —— 模型、终端、压缩、记忆全都有内置默认值（built-in defaults）。问题在于，默认值只适合「先试试看」：一旦你要换模型、要接自己的 API Key，或者要把 agent 改造成你要的样子，就得知道这些设置到底存在哪儿。

文档把配置按「是不是机密」和「属于谁」分成了几类文件：普通设置进 config.yaml，机密进 .env，OAuth 凭据进 auth.json，agent 的身份定义进 SOUL.md，其余目录各自负责记忆、技能、定时任务、会话和日志。理解这个划分，你既不会把密钥写进会被随手提交或分享的文件里，出问题时也马上知道该去查哪个文件。

还有一件容易被忽略的事：配置不是改完就生效。CLI 和 gateway（消息网关）的读取时机不一样，有的键改了要重启，有的键下一条消息就生效。本节把「优先级」和「生效时机」两件事讲清楚，你就能预测某一项设置最终取到什么值，也能在改完之后确认它真的起作用了。

02先认清 ~/.hermes/ 这个目录#

文档用 ~/.hermes/ 表示 Hermes 的数据目录，里面每一个条目的职责都是定死的。你不需要记住内容，但要知道「哪类东西该去哪个文件找」——这是后面所有配置操作的地图。

在 Windows 原生安装下，这个目录就是 %USERPROFILE%\.hermes（也就是 ~/.hermes）。文档特意说明，%LOCALAPPDATA%\hermes 是可丢弃的基础设施（程序本体、Python、Node、便携 Git），可以删掉重装；而 %USERPROFILE%\.hermes 是你的数据——配置、记忆、技能、会话历史。把这个目录同步到别的机器，你的 Hermes 就跟着迁移过去了。

如果要让 Hermes 把数据放在别处，就覆盖 HERMES_HOME 环境变量，指向另一个数据目录即可。

text~/.hermes/ 目录结构（来自文档原文）

├── .env          # API 密钥和机密

# 只想先看普通设置，可以打开 config.yaml

程序装在哪和数据放在哪是两个位置：%LOCALAPPDATA%\hermes 是基础设施（删了能恢复），%USERPROFILE%\.hermes 才是你的数据。备份、迁移、排错都看后者。

03谁说了算：配置优先级（precedence）#

同一个设置可能被写在好几个地方，此时 Hermes 按固定顺序解析，优先级从高到低。记住这个顺序，你就能解释「我明明在 config.yaml 里写了，为什么没生效」这类问题。

文档给出的经验法则是：机密（API 密钥、bot token、密码）放入 .env；其他所有内容（模型、终端后端、压缩设置、内存限制、工具集）放入 config.yaml。当两者都设置了同一项非机密配置时，config.yaml 优先。

bash最高优先级：单次调用用 CLI 参数覆盖
hermes chat --model anthropic/claude-sonnet-4
  • CLI 参数 —— 例如 hermes chat --model anthropic/claude-sonnet-4，仅对这一次调用生效
  • ~/.hermes/config.yaml —— 所有非机密设置的主配置文件
  • ~/.hermes/.env —— 环境变量的回退；机密（API 密钥、token、密码）必须放这里
  • 内置默认值 —— 未设置任何内容时的硬编码安全默认值
经验法则

机密放 .env，其余放 config.yaml。当两者都设置时，config.yaml 对非机密设置优先。

04用 hermes config 查看和修改#

日常操作基本用不到手写 YAML，hermes config 这一组子命令就够了。文档列出的查看、编辑、设置、检查、迁移五种用法如下。

其中 hermes config check 和 hermes config migrate 是给「升级之后」用的：新版本会新增配置项，check 帮你找出缺失的选项，migrate 则交互式地把缺失项补齐——它还会顺带扫描所有已启用的技能，找出尚未配置的技能设置并提供提示。

除了配置本身，还有两条命令值得知道：hermes doctor 用来诊断配置和依赖问题，hermes auth 用来管理凭据（添加、列出、删除、重置、设置策略），并处理 Codex/Nous/Anthropic 的 OAuth 流程——auth.json 里的东西就是它管的。

bash配置管理的五个常用子命令（文档原文示例）
hermes config            # 查看当前配置
hermes config edit       # 在编辑器中打开 config.yaml
hermes config set KEY VAL # 设置特定值
hermes config check      # 检查缺失选项（更新后使用）
hermes config migrate    # 交互式添加缺失选项

# 示例：
hermes config set model anthropic/claude-opus-4
hermes config set terminal.backend docker
hermes config set OPENROUTER_API_KEY sk-or-...   # 保存到 .env
不用纠结写进哪个文件

hermes config set 命令会自动将值路由到正确的文件 —— API 密钥保存到 .env，其他所有内容保存到 config.yaml。另外 hermes config show 会在「技能设置」下显示所有技能设置及其所属技能。

05在 config.yaml 里引用环境变量#

有时候设置项的值本身就是机密（比如辅助模型、委托用的 API Key），或者你想让同一个地址在配置文件里被复用。这时可以在 config.yaml 里用 ${VAR_NAME} 语法引用环境变量。

语法上有几个边界要注意：单个值里可以有多个引用，例如 url: "${HOST}:${PORT}"；如果引用的变量未设置，占位符将保持原样（${UNDEFINED_VAR} 保持不变）；并且仅支持 ${VAR} 语法 —— 裸 $VAR 不会被展开。

yaml在 config.yaml 中引用环境变量（文档原文示例）
auxiliary:
  vision:
    api_key: ${GOOGLE_API_KEY}
    base_url: ${CUSTOM_VISION_URL}

delegation:
  api_key: ${DELEGATION_KEY}
占位符没被替换？

如果 ${UNDEFINED_VAR} 原样出现在配置里，说明这个变量没被设置（例如根本没写进 .env）。另外记得只有 ${VAR} 这种带花括号的写法会被展开。

06SOUL.md：agent 的身份，以及其他上下文文件#

SOUL.md 不存设置，它存「agent 是谁」。文档说明它占据系统提示词的第 #1 槽位，完全替换内置的默认身份——编辑它就是彻底自定义 agent。如果 SOUL.md 缺失、为空或无法加载，Hermes 会回退到内置默认身份；文件不存在时它还会自动生成一份默认的 SOUL.md。

除了 SOUL.md，Hermes 还会读取项目级的上下文文件（context files）来获得项目特定指令和编码规范。这类文件走一套优先级系统：仅加载一种类型，第一个匹配优先，顺序是 .hermes.md → AGENTS.md → CLAUDE.md → .cursorrules；而 SOUL.md 始终独立加载。

AGENTS.md 是分层的：如果子目录里也有 AGENTS.md，所有都会被合并进来。所有加载的上下文文件上限为 20,000 字符，超出部分会进行智能截断。

文件用途范围
SOUL.md主要 agent 身份 —— 定义 agent 是谁（系统提示词第 #1 槽位）~/.hermes/SOUL.md 或 $HERMES_HOME/SOUL.md
.hermes.md / HERMES.md项目特定指令（最高优先级）向上走到 git 根目录
AGENTS.md项目特定指令、编码规范递归目录遍历
CLAUDE.mdClaude Code 上下文文件（也会检测）仅工作目录
.cursorrulesCursor IDE 规则（也会检测）仅工作目录
.cursor/rules/*.mdcCursor 规则文件（也会检测）仅工作目录
改完身份要新会话

记忆和身份这类数据在会话开始时作为冻结快照注入，会话中途的写入不会修改已构建的系统提示词——要等新会话开始（或强制重建）才生效。

07几个你很快会用到的设置键#

配置项很多，下面这几组是新手最先会碰到的。它们都在 config.yaml 里，键名和默认值都取自文档。

记忆（memory）决定 Hermes 能记住多少东西：memory_char_limit 管持久记忆，user_char_limit 管用户画像，单位是字符，文档同时给出了大致 token 换算。压缩（compression）决定长对话怎么被自动摘要，threshold: 0.50 表示用到上下文限制的一半时就开始压缩。

安全相关的两个开关默认值是「保守」的：redact_secrets 默认关闭（只有当你想给工具输出里的真实凭据加一层安全网时才打开），tirith_enabled 默认打开（终端命令执行前由 Tirith 扫描危险操作）。timezone 留空表示用服务器本地时间，它会影响日志时间戳、cron 调度和系统提示词里的时间注入。

yaml把常见的几组键写在一起（键名与默认值来自文档）
timezone: ""                  # IANA 时区，例如 "America/New_York"；默认 "" = 服务器本地时间

memory:
  memory_enabled: true
  user_profile_enabled: true
  memory_char_limit: 2200    # ~800 tokens
  user_char_limit: 1375      # ~500 tokens

terminal:
  backend: local             # local | docker | ssh | modal | daytona | vercel_sandbox | singularity
  timeout: 180               # 每条命令的超时时间（秒）

security:
  redact_secrets: false      # 在工具输出和日志中脱敏 API 密钥模式（默认关闭）
  tirith_enabled: true       # 为终端命令启用 Tirith 安全扫描
键作用默认值
memory.memory_enabled启用持久记忆true
memory.memory_char_limit持久记忆字符上限（约 800 tokens）2200
memory.user_char_limit用户画像字符上限（约 500 tokens）1375
skills.guard_agent_created扫描 agent 创建/修改的技能内容，命中危险模式时先弹出审批false
security.redact_secrets在工具输出和日志中脱敏 API 密钥模式false
security.tirith_enabled为终端命令启用 Tirith 安全扫描true
terminal.backend终端命令在哪里执行（local 为默认后端，无隔离）local
compression.enabled / threshold自动压缩长对话 / 在上下文限制的此百分比时压缩true / 0.50
timezoneIANA 时区，影响日志时间戳、cron 调度和系统提示词时间注入""（服务器本地时间）
local 后端没有隔离

默认的 local 后端下，命令直接在你的机器上运行，agent 拥有与你用户账户相同的文件系统访问权限。文档建议：用 hermes tools 禁用不需要的工具，或切换到 Docker 后端做沙箱隔离。

08改完怎么生效#

这是最容易被忽略的一步。文档明确写着：现有聊天不会重新读取配置——配置改动只对新的会话生效。CLI 里，退出并重新启动即可；gateway（Telegram、Discord、Slack 等）里，下一个新会话生效，如果要强制所有会话都用新配置，就重启 gateway：hermes gateway restart；在 gateway 会话中也可以直接用 /restart。

只有少数键是热重载（hot reload）的：文档说明，在运行中的 gateway 上编辑 config.yaml 中的 model.context_length 或任何 compression.* 键，会在下一条消息时生效——无需 gateway 重启、/reset 或会话轮换，因为缓存的 agent 签名包含这些键，gateway 检测到更改会透明地重建 agent。API 密钥和工具/技能配置仍需要通常的重载路径。

改的是 .env 里的密钥、又不想重启时，用 /reload 斜杠命令：它会把 .env 变量重新加载到运行中的会话，无需重启即可获取新 API 密钥。工具或技能的变更则用 /reset 以更新后的 toolset 启动新会话，/reload-skills 可以重新扫描 ~/.hermes/skills/ 来发现新装或已删除的 skill。

  • 配置变更（gateway）：/restart，或重启 gateway（hermes gateway restart）
  • 配置变更（CLI）：退出并重新启动
  • 新 API 密钥（.env）：在运行中的会话里用 /reload 重新加载
  • 工具 / skill 变更：用 /reset 启动新会话，或 /reload-skills 重新扫描 skills 目录
  • 只有 model.context_length 与 compression.* 这类键，在运行中的 gateway 上编辑后下一条消息即生效
改完先确认

改完先跑一次 hermes config 看当前值对不对，再用 hermes doctor 诊断配置和依赖问题；如果怀疑是配置写坏了，hermes chat --ignore-user-config 会忽略 ~/.hermes/config.yaml 并用内置默认值启动（.env 中的凭据仍会加载），方便对照排查。

常见坑

01我把 API Key 直接写在 config.yaml 里了，可以吗？+

不建议，也不符合文档约定：机密（API 密钥、token、密码）必须放 .env，config.yaml 只放非机密设置。用 hermes config set OPENROUTER_API_KEY sk-or-... 这类命令时不用担心写错地方——hermes config set 会自动把 API 密钥保存到 .env，其他所有内容保存到 config.yaml。

02改完 config.yaml，当前这个会话怎么一点变化都没有？+

这是预期行为。现有聊天不会重新读取配置：gateway 是下一个新会话生效，需要立即对所有会话生效就 hermes gateway restart（或会话里 /restart）；CLI 则退出并重新启动。只有 model.context_length 和 compression.* 这类键在运行中的 gateway 上编辑后下一条消息就生效，不需要重启。

03config.yaml 里的 ${GOOGLE_API_KEY} 没有被替换成真正的密钥？+

两种可能：一是这个变量没有设置，此时占位符会保持原样（文档明确说 ${UNDEFINED_VAR} 保持不变），检查它是否写进了 .env；二是写法不对，只有 ${VAR} 这种带花括号的语法会被展开，裸 $VAR 不会被展开。

04同一项设置在好几个地方都写了，到底哪个赢？+

按优先级从高到低：CLI 参数 > ~/.hermes/config.yaml > ~/.hermes/.env > 内置默认值。所以单次调用可以用 --model 之类的 CLI 参数临时覆盖；而当 config.yaml 与 .env 都设置了同一项非机密设置时，config.yaml 优先。

05升级 Hermes 之后，配置文件里好像少了新版本的选项？+

用 hermes config check 检查缺失选项（文档建议在更新后使用），再用 hermes config migrate 交互式添加缺失选项。migrate 还会扫描所有已启用的技能，找出未配置的技能设置并提供提示——技能自己的非机密设置存在 config.yaml 的 skills.config 命名空间下。
